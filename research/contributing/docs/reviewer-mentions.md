# 8. 成功作者會 @ reviewer 嗎？

**會，但不是每位成功作者都會，也沒有查到必須點名真人 reviewer 的規定。** 本次成功案例中的點名，主要用來回報修正、請求再審查或釐清技術問題。不能把所有 `@` 都當成催審。

## 抽查結果：67 個成功 PR 中，5 個有點名

從第三季研究資料的 109 位外部作者，各取該季最早提出的一個 PR，檢查作者在主討論串與程式碼逐行留言中的點名。資料查核日為 2026-10-28；「成功」指已合併。

| 截止時的結果               | PR 數 | 作者曾 @ 真人 reviewer 或維護者 | 未觀察到這類點名 |
| -------------------------- | ----: | ------------------------------: | ---------------: |
| 已合併                     |    67 |                       5（7.5%） |               62 |
| 尚未合併，含已關閉與仍開啟 |    42 |                      6（14.3%） |               36 |

這是每位外部作者各一筆的樣本，不是全站 PR 統計，也不是隨機抽樣。沒有點名的成功 PR 很多，因此 **@ 不是這批案例的必要條件**。未合併組的比例較高，也不能解讀成點名會降低成功率：爭議較多或等待較久的 PR，本來就可能需要更多溝通。

人工核讀了 11 個 PR 的 16 則候選留言，確認都有實際點名；其中也包含關閉原因的說明。這個數字衡量「有沒有提到對方」，不衡量「有沒有主動要求對方審查」。

## 文字點名和正式邀請審查是兩回事

留言中的 `@帳號` 是文字提及。GitHub 的 **Request review** 則是在 Reviewers 面板提出正式審查請求，會留下獨立事件；GitHub 文件指出，提出這類請求需要儲存庫寫入權限。外部作者不一定有這個權限。[GitHub 官方說明](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/requesting-a-pull-request-review)

Ultralytics 的自動審查指南要求處理建議，並說明必要時可重新請求 UltralyticsAssistant 審查。這是自動化帳號的流程，不代表每個 PR 都必須 @ 真人維護者。此次沒有查到強制點名真人的規定。[官方貢獻指南](https://github.com/ultralytics/ultralytics/blob/main/CONTRIBUTING.md#-automated-review)

## 你可以怎麼做？

以下是依案例整理的建議，不是官方新增規定：

1. 有人審查後，先完成修正與驗證，再回覆原討論。
2. 需要對方再看時，可以點名原 reviewer，附上改動摘要與驗證結果。
3. 尚未有人審查時，先確認範圍、重現步驟與 CI 是否清楚；若要點名，說明為什麼需要這位維護者的意見。
4. 避免沒有新資訊就反覆催審，也不要一次點名多位無關的人。

例如，你可以依實際情況寫：

> @reviewer 已依建議把修改縮到 X，移除 Y，並完成 Z 驗證。這版已準備好再審查，方便時請再看，謝謝。

## 資料與判讀限制

- 樣本來自[第五章的作者事前紀錄分組](merge-rates.md)，不是以當前 CONTRIBUTOR 標籤判斷首次貢獻。外部分組也不等於已查證的雇用身分。
- 只計入作者在合併或關閉前發出的主討論與逐行留言；仍開啟的 PR 使用原始 cohort 快照截止時間。排除最後編輯時間晚於截止的候選留言。
- 真人目標依公開 reviewer、維護者、合併者及正式受邀使用者判定；排除作者自己與已辨識的自動化帳號。程式先移除程式碼及引用，再找出候選，由人工核讀正例。
- 沒有檢查 PR 描述、review 摘要本文、已刪除留言、私訊或其他平台。因此「未觀察到」不等於從未在任何地方點名。
- 公開留言可能曾編輯，API 不能還原所有歷史版本。某人先前沒有出現在此 PR，也不代表雙方第一次接觸。
- 點名的原始資料另行保留正式 review-request 事件；本章表格只統計文字點名，沒有把機器人指令或正式邀請混入。
