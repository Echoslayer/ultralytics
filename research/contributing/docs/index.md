# 先找到可重現的小問題，再提出貢獻

**第一次貢獻 Ultralytics，建議從小範圍錯誤修正或文件改善開始。** 本書幫你找到線索、判斷是否值得投入，再準備維護者能審查的證據。

官方規範偏好範圍小的首次貢獻，包括錯誤修正、效能改善和文件更新。新功能則應先提出議題，取得維護者明確同意。因此，大型新模型或通用架構重整通常需要更多前期投入。[官方貢獻規範](https://github.com/ultralytics/ultralytics/blob/main/CONTRIBUTING.md)

## 先認識書中常用的名稱

| 名稱                  | 本書指的是什麼？                                 |
| --------------------- | ------------------------------------------------ |
| 議題（issue）         | GitHub 上的問題回報或功能提案                    |
| 合併請求（PR）        | 請專案審查並合併一組修改的請求                   |
| 官方專案（upstream）  | `ultralytics/ultralytics`，正式貢獻的對象        |
| 個人副本（fork）      | 你在 GitHub 帳號下複製的專案                     |
| 負責模組（owner）     | 直接控制或觀察問題行為的程式碼位置               |
| 最小可重現範例（MRE） | 別人也能執行、且仍會出現同一問題的最小輸入與程式 |

## 選能公開重現、能比較結果的問題

資料轉換或文件與程式不一致的問題，通常較容易準備公開輸入。匯出、效能與硬體問題也有價值，但你需要相符設備，並先約定比較方式。這是本書依執行與審查成本提出的建議，尚未獲維護者核准為工作項目。

議題標籤只是線索。`bug`（錯誤）仍可能源自外部套件或資料；`enhancement`（改善提案）也不表示已批准新增程式介面。選題時依序做五件事：

1. 重讀議題狀態與最新留言。
2. 用公開輸入重現問題。
3. 找到負責模組。
4. 確認預期行為及其依據。
5. 決定是否修正。

官方也要求回報者提供最小可重現範例。[MRE 指南](https://docs.ultralytics.com/help/minimum-reproducible-example/)

## 研究日期與編寫標準

研究資料查核日期為 **2026-10-28**。本書保存當時讀到的資料，不是完整議題清單，也沒有替你認領工作。

本書採用 **ISO 24495-1:2023** 作為編寫與修訂標準，讓讀者取得需要的資訊、找得到、看得懂、用得上。這是編寫原則，不是 ISO 認證聲明。[標準介紹](https://www.iso.org/standard/78907.html)
