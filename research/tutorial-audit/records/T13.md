## 為什麼是文件缺口，而不是程式問題

- #26283 的目的就是讓「原地修改、大小不變」的情況失效重建，PR 說明也寫了「修改時間也沒變的編輯仍需手動刪除快取」。程式行為是刻意的。
- 那個 PR 只改了 `ultralytics/data/utils.py`，沒動文件；這頁的警告是 [#25919](https://github.com/ultralytics/ultralytics/pull/25919)（2026-08-25）加的，比程式修改早一個月。
- `docs/en/` 裡只有這頁提到快取鍵只看大小。GitHub 上搜尋 `coco-json-training` 與快取相關的 PR，沒有人在處理。

## 使用者不會察覺的舊快取：圖片放在子資料夾

雜湊只看 JSON 與 `img_path` 這個最上層資料夾。若 `file_name` 寫成 `sub/xxx.jpg`，事後把缺的圖片補進 `sub/`，上層資料夾的修改時間不變，快取不會失效（[`probe_t13d.py`](T13-assets/probe_t13d.py)、[`t13d.log`](T13-assets/t13d.log)）：

- JSON 列 4 張、只放 3 張 → 用到 3 張。缺的那張由 `cache_labels()` 直接 `continue`，沒有任何訊息。
- 補進第 4 張再跑 → 仍是 3 張；`get_labels()` 命中快取時也不印任何東西。
- 刪掉 `.cache` 後才是 4 張。

刪除子資料夾裡的圖片同樣不會重建，但載入時找不到檔案會報錯，使用者會發現。

## 準備的修正

分支 `docs/coco-json-cache-mtime`（worktree `.worktrees/coco-json-cache`，基於 `ae2857e3e`），commit `3003c19e3`、`df0fa429b`，共改 6 行：

- 警告改成 note：快取鍵是每個路徑的大小與修改時間，編輯 JSON 會自動重新解析；圖片目錄只算最上層資料夾，直接在底下新增或刪除會重建，原地替換或在子資料夾裡增刪不會；這些情況，以及工具改寫 JSON 後還原修改時間時，要手動刪 `.cache`。
- FAQ 最後一句改成「快取以 JSON 的大小與修改時間為鍵，編輯後會自動重新解析」。

### 送出前逐句驗證

- **Windows（NTFS）：** [`verify_note.py`](T13-assets/verify_note.py) 直接取用修正分支文件裡的 `COCODataset`，以自產圖片逐項測 note 的說法，10 項全部符合（[`verify_win.log`](T13-assets/verify_win.log)）。
- **Linux（WSL2 Ubuntu、ext4）：** WSL 沒有 torch，改用 [`verify_hash_posix.py`](T13-assets/verify_hash_posix.py) 從原始碼抽出 `get_hash` 原樣執行。快取命中與否只由 `get_hash([json, img_path])` 決定，所以只比較雜湊有沒有變（[`verify_linux.log`](T13-assets/verify_linux.log)）。
  - 步驟間沒有間隔時，「在最上層刪除圖片」雜湊沒變：ext4 刪除後資料夾大小仍是 4096，而時間戳每 4 ms 才跳一格，新增與刪除落在同一格。
  - 步驟間隔 50 ms 後，8 項全部符合。實際使用時增刪至少隔數秒，note 的寫法成立。

## 本輪的 miss

第一次測「相同大小的修改」時，連「沒修改」的重跑也重新解析，結果無法判斷。原因是訓練時從 YAML 傳入的路徑用正斜線，我自己建資料集時用反斜線，而雜湊包含路徑字串本身。改用同一個路徑字串重測（`probe_t13b.py`）後才得到乾淨的對照。

## 本輪的教訓

- **程式改了行為，但文件是在更早寫的，這種落差最容易找到。** 查文件說法時，順便用 `git log -L` 看它依賴的函式之後有沒有改過。
- **測快取前，先確認「不修改」的重跑會命中快取。** 沒有這個對照組，任何「有重新解析」的觀察都不能歸因到修改本身。
