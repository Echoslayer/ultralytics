## 挑對象

[R04](R04.md) 建議改從 issue 出發。2026-10-30 列出的 open issue：

- 標 `bug` 的 7 個，多數需要特定硬體（Hailo、IMX500）、長時間訓練（VisDrone 精度），或已有維護者處理（#26916 的對應 PR #26942 已合併，issue 仍開著）。
- 近兩週新開的 13 個，可以在 CPU 上重現的只有兩個：
  - [#26732](https://github.com/ultralytics/ultralytics/issues/26732)：`convert_coco` 靜默去除重複標註。已被改為 feature request，兩人搶著做；其中一人只加日誌的 PR 被關閉，維護者認為現有行為正確。不碰。
  - [#26795](https://github.com/ultralytics/ultralytics/issues/26795)：物體佔畫面 80～90% 時，YOLO26-seg 解出的遮罩無法涵蓋整個物體。只有一張 295×156 的截圖，Y-T-G 問了 `imgsz` 尚無回覆，沒有人重現過。本輪的對象。

## 假設

讀 `ultralytics/utils/ops.py` 的 `process_mask` 與 `process_mask_native`：遮罩由原型與係數相乘後二值化，最後由 `crop_mask` 把框外歸零。若物體很大、預測框比物體小，遮罩就會被框切掉。`imgsz` 越小、原型解析度越低，也可能更明顯。

## 做法

把 `bus.jpg` 裁切到公車佔畫面 50%、80%、90%、98%，各以 `imgsz` 640 與 320、`retina_masks` 開與關推論。替換 `ops.crop_mask`，記下裁切前的遮罩，計算有多少比例的遮罩像素落在框外，也就是被裁掉的部分。

公車在原圖中已橫跨全寬（x 5～807，寬 810），所以只有垂直方向的比例會照設定改變。

## 結果

| 公車佔比 | 被框裁掉的遮罩像素（4 種設定的範圍） |
| --- | --- |
| 50% | 0.30%（`imgsz=320` 沒偵測到公車） |
| 80% | 0.70%～0.91% |
| 90% | 0.61%～1.68% |
| 98% | 0.68%～1.20% |

物體越大，被裁掉的比例略增，但最多不到 2%。`fill90.jpg` 中遮罩完整涵蓋公車，邊緣沒有看得出來的缺塊。這個場景無法重現 issue 描述的現象。

## 為什麼不留言

沒有重現，留言只能猜。issue 寫的是「解碼出來的 mask」，可能是使用者自行解碼 ONNX 輸出，但這也只是推測。維護者已經問了關鍵資訊，等使用者回覆即可。

## 本輪的教訓

- **從 issue 出發，卡在資料。** 可重現的 bug 多半已有人處理；沒人處理的，常是缺少重現資料的問題。
- **替換內部函式來觀察，比只看最終輸出更快。** 這次直接量到框裁切的影響，不必憑疊圖判斷。
- 五輪都沒有找到可送出的缺陷。產出 PR 的仍是 T01–T11 那種「照文件一步步實際操作」。下一步可以回到那個做法，挑之前沒走過的文件頁。
