# R01：#26942 與 #26939 的推論路徑

日期：2026-10-30。基準：官方 main `ae2857e3e`（8.4.193）。環境：Windows 11、Intel Core Ultra 7 265H、Python 3.13.14、torch 2.15.0+cpu、onnxruntime（uv 解析的最新版）。腳本：[`probe_r1.py`](R01-assets/probe_r1.py)；日誌：[`r1.log`](R01-assets/r1.log)。

**結論：三個假設都沒有可送出的貢獻。** P1 重現了副作用，但那是維護者在 PR 中討論後接受的取捨。

## 對象

近兩週（2026-10-16 起）合併、改到 `ultralytics/` 的 PR 約 60 個，多數是外部貢獻者的單行修正。本輪挑兩個推論路徑上的改動：

- [#26942](https://github.com/ultralytics/ultralytics/pull/26942)：CPU 上用 ONNX Runtime 或 OpenVINO 推論時，`BasePredictor.setup_model` 執行 `torch.set_num_threads(min(2, torch.get_num_threads()))`。
- [#26939](https://github.com/ultralytics/ultralytics/pull/26939)：改寫影片 `vid_stride` 的讀幀迴圈與總幀數；所有匯出格式載入時，以 metadata 中 `imgsz` 的長邊作為預設 `imgsz`。

## 結果

| 探針 | 假設 | 觀察 | 判斷 |
| --- | --- | --- | --- |
| P1 | ONNX 推論後，整個 process 的 torch 執行緒被限制，後續 PyTorch 工作變慢 | 執行緒 16 → 2；1024×1024 矩陣乘法 19.9 → 40.3 ms | 重現，但已被接受，不送 |
| P2 | `vid_stride` 新迴圈讀錯幀或漏最後一段 | 10 幀影片在 stride 1、2、3、4、10、11 下讀到 0、s、2s…，全部正確 | 沒有缺陷 |
| P3 | 非正方形或動態匯出套用長邊 `imgsz` 後推論失敗 | `[96, 128]` 靜態、`[96, 128]` 動態、`96` 正方形都能推論，預設值為 128、128、96 | 沒有缺陷，與文件一致 |

## P1 為什麼不送

[#26942](https://github.com/ultralytics/ultralytics/pull/26942) 的正文寫明這個上限作用於整個 process，與 `select_device` 既有做法相同，並在 [#26916](https://github.com/ultralytics/ultralytics/issues/26916) 討論過。作者在留言中主動提出「改成不自動設定，只在文件建議手動設定」的選項；pderrenger 偏好這個選項，理由正是同一 process 混用多個模型時，隱性改動整個 process 的設定有風險。最後合併的版本仍保留自動上限，只補上 `min(2, …)`，讓 1～2 核機器不會增加執行緒。

探針重現的就是他們討論過的混用情境。現在送修正等於重開已拍板的決定。

## 本輪的教訓

- **先讀 PR 討論，再寫探針。** P1 的答案在 PR 留言裡，讀兩分鐘就能刪掉這個假設。
- **探針先印觀察，不急著寫 assert。** P2 第一次跑時顯示 MISMATCH，原因是我把 `len()`（批次數）當成幀數，不是程式錯。腳本已改為檢查 `ds.frames`，重跑結果見 [`r1-fixed.log`](R01-assets/r1-fixed.log)，六個 stride 皆 OK；原始 [`r1.log`](R01-assets/r1.log) 保留作為 miss 的證據（`docs/misses.jsonl` 的 `2026-10-30-01`）。
- **P3 的 `predictor.imgsz` 是設定值，不是實際張量大小。** 要驗證實際輸入形狀，得改看前處理後的張量。
